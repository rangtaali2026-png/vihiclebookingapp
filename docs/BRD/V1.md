# Business Requirements Document (BRD)

**Project Name:** Enterprise Plant Vehicle Booking & Fleet Management System

**Document Version:** 1.0

**Target Platform:** Responsive Web Application (wrapped for Android / iOS mobile clients)

**Architecture Model:** Multi-Tenant / Multi-Site Isolated Architecture

---

## 1. Executive Summary & Project Objectives

Manufacturing facilities require strict coordination of transport resources across shift changes, vendor site visits, intra-plant logistics, and inter-city transport. This system delivers a unified, multi-site vehicle booking application designed for high uptime, minimal administrative overhead, and full accountability.

### Core Objectives

* Eliminate manual logbooks and fragmented phone-based transport requests.
* Automate capacity management, multi-passenger booking, and rule-based vehicle allotment.
* Provide instant omnichannel notifications (WhatsApp, SMS, Email) across approval, dispatch, and trip lifecycles.
* Guarantee complete data isolation across multiple manufacturing plants/sites under a single enterprise instance.

---

## 2. User Roles & Permission Matrix

| Role | Scope | Permissions & Core Capabilities |
| --- | --- | --- |
| **Employee (Requester)** | Plant / Site specific | Create bookings (Private / Shared), add/remove co-passengers within seat limits, view booking history, repeat previous bookings (1-click re-book), modify/cancel requests, self check-in/out, rate completed trips. |
| **Driver** | Assigned Site & Trips | View assigned trips and real-time manifests, view pickup/drop locations, record passenger boarding attendance, mark trip started/completed. |
| **Plant Transport Admin** | Assigned Plant / Site | Manage site vehicle inventory and drivers, review and reallocate bookings, override auto-allotments, cancel bookings, create bookings on behalf of employees, pull utilization and audit reports. |
| **Super Admin** | Enterprise-wide (All Plants) | Create and provision plant sites, enforce multi-tenant isolation, configure site-level approval and allotment rules, manage SMS/WhatsApp/Email gateways, webhooks, and enterprise user credentials. |

## 4. Functional Specifications

### 4.1 Employee / Requester Module

* **Booking Flow:**
* Select trip type: **Shared** (open for auto-grouping or co-passenger additions) or **Private** (exclusive business/confidential travel).
* Input Origin / From Location (internal plant gate, workshop, admin building, or external address) and Destination / To Location.
* Define departure date/time, expected return date/time (for round trips), and trip purpose/cost center.


* **Participant Capacity Control:**
* Select vehicle category (e.g., Car 4-seater, SUV 6-seater, Bus 42/52-seater).
* Add, edit, or remove employee participants via employee ID lookup.
* Validation rule: Form restricts total passengers to strictly $\le$ `Vehicle Max Capacity - 1` (retaining 1 seat for the driver).


* **Trip History & Fast Re-Book:**
* View tabbed booking states: `Pending`, `Approved`, `In Progress`, `Completed`, `Cancelled`.
* **Fast Re-Book Button:** Replicates origin, destination, vehicle category, and standard participants from any completed trip into a pre-filled new draft with 1 click.


* **Modifications & Self-Service Check-In:**
* Modify pickup times or passenger lists up until admin lock or trip dispatch.
* Mobile check-in/check-out button active during trip window.
* Automated delivery of a 1-to-5 star rating and feedback form upon trip closure.



---

### 4.2 Driver Operations Module

* **Assigned Trip Manifest:**
* Clean, mobile-first daily run sheet displaying scheduled pickup times, route endpoints, and total authorized headcount.


* **Passenger Attendance Verification:**
* Digital passenger checklist: Driver toggles "Boarded / Absent" for each tagged participant at departure.


* **Trip Lifecycle Execution:**
* Status triggers: `Start Trip` $\rightarrow$ `Arrived at Destination` $\rightarrow$ `Complete Trip`.
* Real-time sync with admin monitoring dashboard.



---

### 4.3 Plant Transport Admin Module

* **Fleet Inventory Management:**
* CRUD operations for site-specific vehicles: Registration number, vehicle make/model, classification (Sedan 4-seater, SUV 6-seater, Mini-bus 20-seater, Bus 42-seater, Bus 52-seater), operational status (`Active`, `Under Maintenance`, `Decommissioned`).
* Driver profile management: Name, mobile number, license class, license validity expiry, active status.


* **Allotment & Dispatch Control:**
* Real-time dashboard showing incoming requests.
* **Override Mechanism:** Admin can change the auto-allotted vehicle or assigned driver, split bookings, or reject/cancel with mandatory reason logging.
* **Proxy Booking:** Admin can initiate and confirm bookings on behalf of plant executives, guests, or offline plant staff.


* **Reporting & Analytics Engine:**
* On-demand and scheduled exports (`.XLSX`, `.CSV`, `.PDF`):
* **Daily Dispatch Report:** Vehicle run sheets, driver allocations, and gate logs.
* **Weekly/Monthly Vehicle Utilization Report:** Total operational hours, idle hours, capacity utilization rate ($\frac{\text{Actual Passengers}}{\text{Seat Capacity}}$), and maintenance downtime.
* **No-Show & Cancellation Log:** Track unused vehicle runs and unboarded passengers.





---

### 4.4 Super Admin & Multi-Site Governance Module

* **Site Provisioning Engine:**
* Create new plant replicas (e.g., Plant 1, Plant 2, Corporate HQ) via frontend console.
* Generate site tokens, assign local site admins, and establish dedicated site partitions.


* **Configurable Workflow Engine (Per Site):**
* **Auto-Allotment:** `Enabled` / `Disabled`. (When enabled, matches smallest available vehicle meeting passenger count and route window).
* **Approval Hierarchy:** Toggle between `Auto-Approve Requests`, `Admin Approval Required`, or `Manager + Transport Admin Dual Approval`.


* **Enterprise Gateway & Webhook Manager:**
* **WhatsApp Business API:** Endpoint URL, Access Token, and pre-approved template ID configuration.
* **SMS Gateway:** HTTP API / SMPP endpoint, auth credentials, Sender ID / DLT template mapping.
* **Email Relay:** SMTP server settings, port, encryption type (TLS/SSL), and sender address.
* **Outbound Webhooks & Dispatch:** Configurable webhook triggers (`booking.created`, `booking.approved`, `trip.completed`) for ERP/SAP integration.


* **Identity & Access Management (IAM):**
* Bulk creation, credential reset, and role assignment for users across all operational plants.

## 6. Non-Functional & Technical Requirements

* **Performance & Concurrency:** System must support 500+ concurrent requests per site with end-to-end booking confirmation turnaround under 2 seconds (excluding external messaging latency).
* **Security & Compliance:**
* Role-Based Access Control (RBAC) enforced on both API and presentation layers.
* Encrypted communication (HTTPS/TLS 1.3) and encrypted sensitive credentials (passwords, gateway API tokens) at rest using AES-256.
* Immutable audit log tracking vehicle reassignments, cancellations, and administrative overrides.


* **Availability:** 99.9% uptime target suitable for continuous 24/7 round-the-clock manufacturing operations.

# Business Requirements Document (BRD) — Addendum: QR Code Passenger Attendance

**Module Reference:** Section 4.5 — Physical Vehicle QR & Self-Service Attendance Verification

**Applies To:** Plant Vehicle Inventory, Driver Cab Operations, Requester Boarding Flow

---

## 1. Feature Overview & Architecture

To eliminate driver manual entry bottlenecks during peak manufacturing shift movements, each physical vehicle is assigned a permanent, unique QR code upon inventory creation.

The physical QR decal is affixed inside the vehicle cabin (dashboard, back of headrest, or near passenger entry). Boarding passengers scan this QR using any standard smartphone camera or the wrapped mobile app, which immediately routes to a lightweight web verification page.

```
+-----------------------------------------------------------------------------------+
| 1. Vehicle Created in Admin Console                                               |
|    └─ System generates UUID + dynamic signing key -> Vector PDF/SVG QR Decal      |
+-----------------------------------------+-----------------------------------------+
                                          |
                                          v
+-----------------------------------------------------------------------------------+
| 2. QR Decal Affixed in Vehicle Cabin                                              |
|    └─ Driver displays QR sticker inside vehicle                                   |
+-----------------------------------------+-----------------------------------------+
                                          |
                                          v
+-----------------------------------------------------------------------------------+
| 3. Passenger Scans QR at Boarding                                                 |
|    └─ Browser redirects to: https://plant-transit.company.com/attend?v={vehicle_id}|
+-----------------------------------------+-----------------------------------------+
                                          |
                                          v
+-----------------------------------------------------------------------------------+
| 4. Validation & Cross-Check Layer                                                 |
|    ├─ Inputs: Employee ID / Badge Number + Registered Mobile Number               |
|    ├─ Auto-Detect: Checks Active/In-Progress Trip assigned to this vehicle        |
|    ├─ Validation Rules:                                                           |
|    │   ├─ Match: Employee is listed in booking participants -> PASS               |
|    │   ├─ Capacity Check: (Current Checked-In < Vehicle Max Capacity) -> PASS     |
|    │   └─ Mismatch: Employee not in manifest OR already checked in -> REJECT/WARN |
+-----------------------------------------+-----------------------------------------+
                                          |
                                          v
+-----------------------------------------------------------------------------------+
| 5. State Mutation & Real-Time Sync                                                |
|    ├─ Mark employee status: `Boarded / Present` (with GPS & timestamp)            |
|    ├─ Increment Real-Time Vehicle Occupancy: (e.g., 4 / 6 Seats Occupied)         |
|    └─ Push live update to Driver Manifest UI & Admin Fleet Dashboard             |
+-----------------------------------------------------------------------------------+

```

## 2. Functional Requirements

### 2.1 Vehicle QR Code Generation & Management (Admin Module)

* **Trigger:** Instant generation upon successful vehicle registration (`POST /api/v1/vehicles`).
* **Payload Encoding:** Encodes a secured URL containing the encrypted vehicle reference and plant site token:

$$\text{Target URL} = \text{[https://transit.plant.internal/scan?vid=VID](https://transit.plant.internal/scan?vid=VID)\_94821\&site=SITE\_BARODA\&sig=HMAC\_SHA256}$$


* **Format & Export:**
* Admin console provides 1-click **Download Printable Decal (A6 / Sticker Size PDF / PNG)** with vehicle registration number, seat capacity, and plant site name clearly printed under the QR code.
* **Regeneration Option:** If a QR decal gets damaged or compromised, Admin can regenerate the token, immediately invalidating the prior QR code.



---

### 2.2 Passenger Scan & Attendance Landing Page (Mobile Web)

* **Zero-App-Requirement:** Must operate in any standard mobile browser (Chrome, Safari) without requiring prior app installation or enterprise login session.
* **Input Fields:**
* **Employee ID / Badge Number** (alphanumeric, auto-capitalized).
* **Mobile Number** (10-digit validation).


* **Automatic Session Lookup:**
* System evaluates current server timestamp against scheduled trip windows for the scanned `vehicle_id`.
* Matches active trips marked `Dispatched` or `In-Progress` within a $\pm 45\text{-minute}$ operational buffer.



---

### 2.3 Cross-Verification & Occupancy Engine

* **Match Found:**
* If `(Employee ID + Mobile)` matches an authorized participant on the active trip manifest:
1. Update passenger record from `Awaiting Boarding` to `Boarded`.
2. Record exact timestamp and device user-agent.
3. Update vehicle live occupancy counter:

$$\text{Live Occupancy} = \sum \text{Boarded Passengers}$$


4. Display instant green confirmation screen to employee: *"Check-in Successful — Seat Confirmed on [Vehicle No.]"*.




* **Exception Handling & Walk-In Overflows:**
* **Not in Manifest:** If an employee is not on the passenger manifest, check if vehicle has remaining capacity ($\text{Live Occupancy} < \text{Vehicle Capacity}$). If space permits and booking is marked `Shared`, prompt: *"Unscheduled passenger — request driver approval to board"*, flagging as an *Unscheduled Boarding* on the audit report.
* **Duplicate Scan:** If already checked in, displays: *"Already Checked In at HH:MM"*.
* **No Active Trip:** If the vehicle has no trip dispatched for that time slot, displays: *"No active trip assigned to this vehicle. Contact Transport Desk"*.



---

### 2.4 Driver & Admin Real-Time Synchronization

* **Driver Manifest Screen:**
* Automatically updates the attendance status in real time via WebSockets without needing a manual refresh.
* Passenger row switches to green with a `Boarded via QR` badge.
* Real-time seat occupancy bar indicator (e.g., **5 / 6 Occupied**).


* **Driver Override:** Driver retains manual authority to mark passenger present or absent in case of phone battery failure or network drop.
* **Plant Admin Live Monitoring:**
* Admin dashboard highlights under-utilized vehicles and no-shows prior to vehicle dispatch from the factory gate.
